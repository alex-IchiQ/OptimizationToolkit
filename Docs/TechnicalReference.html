How Ultimate Optimization Toolkit works

A reference for developers who will maintain or extend the plugin: how a level scan runs, where findings come from, how fixes and Undo work, where the module boundaries are, and what to check first.

version1.1.0 moduleOptimizationToolsetEditor typeEditor · PostEngineInit platformsWin64, Mac UE5.3–5.8 (uplugin: 5.8.0) passes / fixes / actions9 / 10 / 2

Overview

The plugin is editor-only: one module, OptimizationToolsetEditor, with no runtime code, no content (CanContainContent: false) and no Blueprint API. The whole UI lives in one nomad tab, OptimizationToolkit, opened from the Optimize button on the Level Editor toolbar or from Window → Ultimate Optimization Toolkit.

Features come in three families. They don't know about each other and are registered in a shared registry:

IAnalyzePass

A read-only check over the loaded level. Appends FFinding entries to the scan result.

IOptimizationFix

A transactional fix for one finding. Linked to findings by FixId.

ICleanupAction

A project-wide operation not tied to a finding (redirectors, saving packages). Usually not undoable.

On top of these sit five UI pages: Dashboard, Optimize, Analyzer (memory used by loaded content), Profile (stat commands and viewport visualizers) and Clean Up (unused assets and possible duplicates).

The code records why: the scan result and filters used to live on the main window widget, which grew to six panels and about 1,800 lines. Now each page takes only the model and reacts to FToolsetModel::OnChanged() instead of being called directly by whatever changed the state.

Scan lifecycle

The Scan button in the left navigation (SOptimizeShell::OnScanClicked) is the only entry point. It does four things in order:

  1. Model->RunScan(): level analysis that feeds Dashboard and Optimize.
  2. DashboardView->Scan(): FProjectSizeReport::Compute() and a refresh of the level tree.
  3. AnalyzerView->Scan(): FMemoryReport::Compute().
  4. CleanupView->Scan(): an Asset Registry walk under /Game, behind a cancellable slow-task dialog.

Details that matter:

  • One world walk. Passes don't run their own TActorIterator; they iterate the context arrays. If a new pass needs another type, add a bucket to FLevelScanContext rather than a second walk.
  • Sub-levels. TActorIterator covers the persistent level and every loaded sub-level. Unloaded ones can't be read at all. Actors in packages excluded on the Dashboard are skipped during the walk.
  • Scope contract. After all passes, ensureMsgf(HasValidScopeTarget(...)) checks that each finding has the target its EFindingScope requires. A mistake in a new pass surfaces immediately instead of in navigation.
  • LevelName is set once by the analyzer from TargetActor, and only for non-persistent levels. Passes never fill it in.
  • Baseline. RunScan() keeps the previous FLevelStats in PreviousStats, so the Dashboard can show deltas, including after the automatic rescan that follows a fix.

Invalidation

FToolsetModel::InvalidateScan() clears the whole result (baseline included) and broadcasts OnChanged. It runs whenever a threshold changes on the Dashboard or a level is toggled in Scanning Scope. This is deliberate: otherwise Optimize could apply a fix to an actor in a level the user just excluded.

For group findings (instancing candidates) the UI hands the fix a copy of the finding with RelatedActors narrowed to the actors the user ticked. If fewer than two are ticked, the group is skipped. The original finding is left unchanged.

Data model

All types live in Public/Toolset/ToolsetTypes.h. The enums are deliberately not UENUMs: they never reach Blueprint or a UPROPERTY. If reflection is ever needed, the names must become globally unique (for example EOptimizationSeverity).

Health score

FScanResult::HealthScore() starts at 100 and subtracts a penalty per finding. Penalties are grouped by TypeId and capped by the worst severity seen for that type. Two hundred movable lights count as one problem, not two hundred.

FLevelStats

The scale of the level, not problems: Actors, Meshes (distinct UStaticMesh assets), Triangles (LOD0 × instance count for ISM/HISM, int64), Materials (distinct, excluding /Engine/ and transient), Lights (every ULightComponentBase, including those on Blueprint actors). Skeletal meshes are deliberately left out of the triangle count because their render data may not be loaded.

FTexturePass Pass_Textures

Collects UTexture2Ds through GetUsedTextures and density through GetStreamingRenderAssetInfoWithNULLRemoval. Each texture uses its largest TexelFactor, its most stretched usage: if a texture's resolution is justified on a wall, extra density on a doorknob is the doorknob's UV problem, not the asset's. Density is TextureSize × 100 / TexelFactor texels per metre. Special-purpose LOD groups (UI, RenderTarget, Lightmap, Shadowmap, LUT, Terrain, Bokeh, IES, Pixels2D) are softened or skipped.

FBlueprintDependencyPass Pass_BlueprintDependencies

For each Blueprint package in the level, walks the graph of hard dependencies only (EDependencyQuery::Hard; the default query also returns soft ones, which was the pass's original bug). /Script/ packages and maps (PKG_ContainsMap) are not walked. A line that looks unnecessary but isn't. EditorModule.GetCurrentRegistrySource() is called only for its side effect. FAssetManagerEditorModule initializes its registry source lazily, while GetIntegerValueForCustomColumn() reads it directly and returns 0 for every package until it is initialized. Without this call the pass silently found nothing until the user happened to open a Size Map. SCleanupView::BuildEntries does the same. Don't remove it.

Auto-fixes

Each fix opens its own FScopedTransaction, calls Modify() before changing anything, and re-checks state first, because the level may have changed between the scan and the click. Apply() returns true only when something actually changed. Asset fixes resolve the mesh with OptimizationFixUtils::ResolveStaticMesh: TargetAsset first, then the first UStaticMeshComponent on TargetActor.

FConvertToInstancesFix in detail

  1. Takes the live AStaticMeshActors from RelatedActors; returns if fewer than two remain.
  2. The first actor is the template. Every actor must pass ComponentsMatch (the pass's key rules, plus the same world and level) and GUnrealEd->CanDeleteActor. Any mismatch aborts the whole fix.
  3. Spawns an empty AActor at the group's centroid in the same level, labelled HISM_<Mesh>, with the same folder and hidden flags.
  4. Creates a UHierarchicalInstancedStaticMeshComponent, copies materials, collision, shadows, visibility, decals, occluder, custom depth, draw distances and lighting channels, registers it as the root component and adds the instances in world space.
  5. Destroys the original actors in reverse order. If an actor can't be destroyed, its instance is removed instead (reverse order keeps indices stable). If none could be destroyed, the holder is removed and the transaction cancelled.

A batch apply is N separate transactions, not one. Undoing an "Apply" over ten findings takes ten Ctrl+Z presses.

Clean Up and reports

Clean Up list (SCleanupView::BuildEntries)

Walks every asset under /Game behind a cancellable dialog. If the Asset Registry is still loading, the state is RegistryBusy. On cancel, partial results are discarded entirely (Cancelled).

Exclusions: packages named in UGameMapsSettings (startup, transition, default and server maps, GameInstance, default GameMode); __ExternalActors__ and __ExternalObjects__ (World Partition); the World and ObjectRedirector classes.

Unused

GetReferencers(..., EDependencyCategory::All), minus the package itself, is empty: nothing references the asset in the Asset Registry. Loading by string path or from config is invisible to this check.

Possible duplicate

Key lower(name)|class|disk size; a group of ≥ 2 assets from ≥ 2 different folders, size > 0. A heuristic for a re-imported pack, not a content hash.

Deletion goes only through ObjectTools::DeleteAssets(..., bShowConfirmation = true): Unreal re-checks references and offers force delete. The list is rebuilt afterwards.

FProjectSizeReport

Package file sizes under /Game, grouped into 9 categories (EAssetCategory). The class → category mapping is an explicit table rather than a name prefix (otherwise "Material" would swallow MaterialParameterCollection); anything unlisted goes to Other. Each package is measured once, attributed to its first asset. Used by the Dashboard and by the group filter on Clean Up.

FMemoryReport

What loaded content costs in memory right now. Sources: RHIGetTextureMemoryStats, the texture streaming manager (pool size, over budget), and TObjectIterator over UTexture2D, UTextureRenderTarget2D, UStaticMesh and USkeletalMesh. Textures report both full and resident size. Here a texture's role (Diffuse, Normal, UI, Lightmap, Other) is guessed from its name. Lists are sorted by size and trimmed to TopN = 200.

Extending the plugin

Adding an analysis pass

// Private/Toolset/Analyzer/Passes/DecalPass.h
class FDecalPass : public IAnalyzePass
{
public:
    virtual FName GetId() const override { return TEXT("Pass_Decals"); }
    virtual void Run(const FLevelScanContext& Context, const FAnalyzeThresholds& T, FScanResult& Out) const override;
};

// .cpp: only read Context, only append to Out.Findings
FFinding F(TEXT("Decal.Overlap"), ESeverity::Minor, ECategory::Materials, EFindingScope::Actor,
    LOCTEXT("Title", "..."), FText::FromString(Actor->GetActorNameOrLabel()));
F.WhyItMatters = ...;
F.HowToFix     = ...;
F.TargetActor  = Actor;          // required for Scope::Actor, otherwise the ensure fires
Out.Findings.Add(MoveTemp(F));

// ToolsetRegistry.cpp, RegisterDefaults()
AddPass(MakeUnique<FDecalPass>());
  • Don't walk the world yourself. If the bucket you need is missing, add it to FLevelScanContext and fill it in AnalyzeCurrentLevel.
  • De-duplicate by asset when the problem belongs to the asset. A hundred actors sharing one mesh should produce one finding.
  • If a check can't run, return a visible finding with scope System (see MakeUnavailableFinding) instead of returning quietly. Silence looks like a clean level.
  • New threshold: a property and Default_* constant in UOptimizationToolsetSettings, a line in ResetToDefaults(), a field in FAnalyzeThresholds, a clamp in the analyzer, and a row in SDashboardView::BuildSettingsCard.
  • For findings with scope Project, add a search string to FFindingNavigator::OpenProjectRenderingSettings.

Adding a fix

class FMyFix : public IOptimizationFix
{
public:
    virtual FName GetId() const override { return TEXT("Fix_MyFix"); }   // = FFinding::FixId
    virtual FText GetLabel() const override;
    virtual bool IsSupported() const override { return GEditor != nullptr; }
    virtual bool Apply(const FFinding& Finding) const override
    {
        UStaticMesh* Mesh = OptimizationFixUtils::ResolveStaticMesh(Finding);
        if (!Mesh || /* already fixed */ ...) { return false; }  // re-check state
        const FScopedTransaction Tx(LOCTEXT("Tx", "My fix"));
        Mesh->Modify();
        // ... changes ...
        Mesh->PostEditChange();
        Mesh->MarkPackageDirty();
        return true;
    }
};

Rules: one transaction per Apply; Transaction.Cancel() on partial failure; no edits to class defaults or project settings from a fix. Anything with a wide blast radius should stay without a FixId, because "Apply" runs everything that's ticked at once.

Adding a Clean Up action

Implement ICleanupAction and call AddAction(...). The panel builds its buttons from the registry. If the action rewrites or deletes assets, return IsDestructive() = true. If Execute() shows its own review dialog, override NeedsConfirmation() to return false so the user isn't asked twice. Check IsLoadingAssets() before relying on the Asset Registry.

Known issues and tech debt

Found while reading the source. The code was not compiled or run, so the build-related items need confirming on the relevant engine version.

Build

AssetManagerEditor plugin dependency is not declared in the .uplugin

Build.cs links the AssetManagerEditor module, but OptimizationToolkit.uplugin has no "Plugins" section listing it. UBT warns about this, and if that plugin is disabled in a project the module may fail to load. That also makes the runtime IAssetManagerEditorModule::IsAvailable() check in BlueprintDependencyPass effectively unreachable. Add {"Name": "AssetManagerEditor", "Enabled": true}.

Build

EAllowShrinking on UE 5.3

BlueprintDependencyPass.cpp calls Pending.Pop(EAllowShrinking::No). As far as I know this enum arrived in 5.4, while the README claims 5.3 support. Build on 5.3 to confirm, or branch with OPTIMIZATION_UE_VERSION_AT_LEAST(5, 4).

UI

Footer version doesn't match the plugin

SOptimizeShell::BuildNav shows a hardcoded v1.0.0, while VersionName in the .uplugin is 1.1.0. Read it via IPluginManager::FindPlugin(...)->GetDescriptor().VersionName instead.

UI

Outdated hint text

SOptimizeView::GetSummaryText says "press Scan Level", but the button is labelled Scan.

Code

Unused filter API in FToolsetModel

GetVisibleFindings, CountForCategory, SetSearchFilter, ToggleSeverity, SetCategoryFilter, PassesCategory and the single ApplyFix are never called: Optimize builds its tree from GetAllFindings(). Either wire the filters into the UI or remove them. The health score isn't shown anywhere either.

Data

The Lights counter and LightingPass count different things

GatherLevelStats counts every ULightComponentBase (SkyLight included), while FLevelScanContext::Lights and the movable light budget use only ULightComponent. Dashboard numbers and findings can disagree.

Data

Two different ideas of a texture's role

FTextureCompressionPass derives the role from the material input, while FMemoryReport on the Analyzer page uses name suffixes (_n, _d and so on). Projects with a different naming scheme will see most textures under Other in Analyzer.

UX

Batch Apply isn't one transaction

Each fix opens its own FScopedTransaction, so undoing a batch takes several Undo steps. An outer transaction in FToolsetModel::ApplyFixes would make it one step.
